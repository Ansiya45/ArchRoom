# Stage C1: local folder controls

Stage C1 adds an administrator-only connection panel and root-scoped folder procedures. It does not authorize a real Google account, alter Drive sharing, or upload recordings. `backend/src/config/recordingDrive.ts` remains the only configured root URL.

## Connection setup before a later live trial

In the same Google Cloud project as the backend OAuth Web client, enable the Google Drive API and Google Picker API. Configure the OAuth consent screen for the company's authorized account and add the backend `/google-drive/oauth/callback` URL as an exact Authorized redirect URI. Configure the web application's Authorized JavaScript origin for the frontend. Use the existing backend variables `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_OAUTH_CALLBACK_URL`, `GOOGLE_INTEGRATION_ADMIN_USER_ID`, and `GOOGLE_INTEGRATION_TOKEN_KEY` only in backend secret management. The browser Picker requires `VITE_GOOGLE_DRIVE_API_KEY` (a website-restricted API key) and `VITE_GOOGLE_DRIVE_APP_ID` (the Cloud project number). The website key's referrer restrictions must allow the frontend origin and Google's Picker iframe at `https://docs.google.com/*`; restrict its API usage to Google Picker API. Do not put the backend client secret or integration token key in frontend variables.

The administrator starts the existing backend authorization-code flow. The company owner consents through Google, without giving the application or developer a password. The temporary access token returned by the administrator-only `pickerAccess` procedure is used only to open Google Picker. Picker selection is sent to `verifyRoot`; only an exact match to the configured root whose backend Drive metadata reports a folder, untrashed, app-authorized, and able to list/create children is persisted as a connection. A shared folder link alone does not grant `drive.file` access. Google may return insufficient capabilities even after Picker selection; the UI then remains disconnected. No broader Drive scope is requested.

The current OAuth state and pending consent are in process memory. A backend restart during setup requires repeating consent; stored encrypted credentials survive restarts. A live trial also requires a single stable backend instance and a browser flow where the OAuth callback can receive the setup cookie (`SameSite=Lax`); validate the deployed frontend/API origin and proxy before setup.

## Application boundary

The backend Drive client fetches only the configured root and its direct child folders. Listing shows the integration administrator all verified direct children; other users see only registered child folders for which they have manager or trainer upload permission. Viewers and unassigned users cannot select protected child folders. Stage C1.1 adds a separate, explicit database grant for creating direct children. The integration administrator can grant or revoke it through the authenticated `recordingFolders.setCreatorGrant` procedure using a YLAAM user ID. A manager assignment on an existing folder does not imply this grant. The integration administrator also retains creation permission. Each created child is registered with a manager assignment for its creator only. The central root saves as `NULL` and remains available for general meeting creators. Non-null destinations are checked again by the backend on meeting create/update. Rescheduling is unchanged, and recording policies remain saved preferences only.

Stage C2 should first validate the live OAuth/Picker/root flow with the approved company account, then verify listing and creation under that root. Grant management has an administrator-only API but no assignment UI yet; an administrator needs the exact YLAAM user ID to grant creation permission. Migration 0015 must be applied to the deployment database before that procedure is used, after separate production approval. Direct Drive sharing, uploads, deletion, and automatic recording remain separate later work.
