# Migration convergence: investigation, not release-ready

The two histories diverge after `0012`. The senior's `0013_org_rbac` and `0014_transcript_recap` have timestamps interleaved with the feature branch's recording migrations. The current runner rejects any absent migration whose timestamp is not newer than the most recent applied timestamp. A sorted union of the journals therefore cannot upgrade either existing lineage safely.

A candidate forward-only design is to retain the original journals and SQL byte identities as immutable lineage inventories, and use a separate, explicit convergence planner. Under the existing migration lock, the planner must identify an exact known history using timestamps and hashes, account for verified CRLF/LF variants, and reject unknown, duplicate, incomplete, or conflicting identities. It must also verify all objects and data assumptions required by that lineage, not merely the journal entries. Each supported lineage would apply independently reviewed forward-only delta migrations with new timestamps after both branches, then enter one common verified baseline. A missing historical entry must never be inserted as if its original SQL had run.

Fresh installations need an explicitly selected baseline and independently checked schema. Senior-only installations need feature changes in dependency order, adapted into reviewed forward deltas where required. All three paths must converge on the same catalog, privileges, constraints, indexes, triggers, and data invariants.

A disposable-cluster-only feature-lineage prototype now exists in `backend/src/db/feature-convergence.ts` and `backend/drizzle/convergence/feature-to-combined-v1.sql`. It verifies pinned historical ledger identities, takes the existing advisory migration lock and exclusive table locks, compares PostgreSQL 17 catalog fingerprints, checks foreign-key relationships, applies the delta and writes a separate execution record in one transaction. It never inserts historical senior migration records. It also creates the recording-consent audit tables from feature migration 0030, which was present in that branch but absent from its journal; the new audit tables enable row-level security and revoke public API access. A rerun checks both the execution record and the resulting fingerprint.

The disposable-only senior path is `backend/src/db/senior-convergence.ts` with `backend/drizzle/convergence/senior-to-combined-v1.sql`. It pins the exact senior ledger identities and reviewed forward SQL, validates the senior catalog and existing foreign keys, applies the missing feature objects in one locked transaction, validates the result, and writes a separate senior convergence record. It does not create historical feature ledger entries. The two test paths create the previously unjournaled 0030 consent tables once and enable their row-level security. Both retain the original branch ledgers.

The journal is the feature-lineage fresh-install baseline. The senior ledger remains separately pinned. The normal runner and readiness checks dispatch to the coordinator only with `NODE_ENV=test` and `PHASE_B_DISPOSABLE_COORDINATOR=1`; all other default runner and readiness uses fail closed. They must not add or replay a historical 0030 journal entry against an already converged schema.

The disposable-only coordinator `backend/src/db/disposable-migration-coordinator.ts` adds an atomic fresh installation and dispatches recognized historical ledgers to the two guarded executors. The fresh path executes and records the real feature migrations, then the feature forward delta and its separate execution record in one transaction. Repeated runs revalidate the ledger, marker, catalog, security snapshot, and foreign-key data. Readiness verifies without applying migrations.

All three prototypes are hard-restricted to a specific disposable cluster. Their fingerprints are PostgreSQL 17 and test-role specific; they do not yet establish portability or cover every possible database object, schema grant, or data invariant. They are not production migrations. Production runner integration, production catalog baseline, and full schema and privilege review remain unimplemented; do not enable them on existing databases.

The PostgreSQL fixtures `backend/tests/disposable/feature-convergence.test.ts` and `backend/tests/disposable/senior-convergence.test.ts` verify ledger and schema drift rejection, a historical foreign-key violation, simulated transactional interruption and retry, representative data retention, a second execution, audit table RLS, and a persisted recording-confirmation query. Their resulting logical catalog fingerprints match after ignoring physical column order and normalizing CRLF/LF in function bodies; strict fingerprints remain lineage-specific. The separately runnable `phase-b-confirmation.test.ts` also supports a verified combined disposable database. These tests do not establish real Drive behavior or production compatibility.

The coordinator fixtures cover fresh installation and feature and senior dispatch, including rollback, rerun, drift, and missing or mismatched execution records. A separate disposable comparison in `disposable-schema-audit.ts` compares schema ownership and ACLs, relation ownership and ACLs, views, sequences, function access, default ACLs, and trigger states across the test schemas. These checks supplement the existing catalog fingerprint and are not an exhaustive security audit.

Production history and schema are unknown. Deployment remains blocked until an authorized administrator exports the migration timestamps and hashes, provides the applicable schema inventory and historical migration bytes, and a reviewed upgrade and rollback plan passes tests on faithful disposable replicas. Do not execute migration commands against the original local or production databases as part of this investigation.
